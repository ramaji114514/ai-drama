# 架构与几个硬约束

## 一条分界线

这个骨架只做**确定性**的事，创意判断全部留给 `skills/`：

| 放在骨架（Python） | 放在 skill（Markdown） |
|---|---|
| 状态机、断点续跑、产物命名与幂等 | 选题、剧名、结构 |
| 成本记账、预算闸门 | 剧本、台词 |
| ffmpeg 拼接/转码/混音/字幕 | 分镜设计、镜头提示词 |
| 并发调度、失败重试与留痕 | 角色设定、影调风格 |
| 质检的**执行**（规则匹配、三态判定） | 质检的**标准**（哪些词不能写） |

判断依据是"它会不会变"：状态机不该每次重写，审美必须每次都能改。
两者通过结构化产物对接 —— **skill 产出 JSON，骨架消费 JSON**
（`runs/<run_id>/episode.json` 人工可编辑，改完 `resume` 接着跑）。

## 为什么视频生成是个注入点

模型能力不可控，而且换得比什么都快。所以骨架**不认识任何厂商**：

```
stages/04_video.py  只调用 VideoProvider.submit/poll
providers/dryrun.py 本地假渲染，零成本跑通全片
providers/_template 接真厂商时照抄的几十行
```

`providers/registry.py` 是唯一的切换入口，`stages/` 一行都不用改。
详见 [adding-a-provider.md](adding-a-provider.md)。

## 角色一致性：三层，缺一层就漂

这是短剧里最容易崩的地方，也是参考项目里翻车最多的地方。

**第一层 · 参考图。** 每个角色渲一张定妆照，后续所有镜头复用同一张。
这是最低成本的方案，只要它**真的被用上**。

**第二层 · 在提示词里点名。** 只把图传给模型不等于它会用。现场记录是
"参考图传了也漂" —— 因为模型每次调用都是独立的，它没有任何机制知道
这一镜和上一镜是同一个人。所以 `core/identity.py` 做三件事：

* `reference_block()` 生成 `@图片1 = 角色「X」本人：脸型五官、发型发色、
  体型必须与这张图完全一致`，编号与传给模型的图片列表**同序**；
* `NOT_INHERIT` 显式排除资产图版式 —— 参考图是白底证件照，不说清楚，
  模型会把白背景、站姿、正面构图、影棚光一起搬进分镜画面；
* `identity_retry_prompt()` 把**具体差异**写进下一版提示词
  （"发型从长发变成短发"比"要一致"有用得多），并且是幂等的，
  重试两次不会把同一段指令叠两遍。

**第三层 · 生成后校验，而且不许假装通过。** `core/identity.py` 的
`parse_identity_verdict()` 把结论分成**三态**：

| 态 | 含义 | 处理 |
|---|---|---|
| `pass` | 查了，通过 | 进成片 |
| `fail` | 查了，不合格 | 按差异重生成 |
| `unchecked` | **没查成**（调用失败/没本地副本/输出读不出来） | **按未通过算**，重跑时补查 |

第三态是整套设计里最重要的一条。"没查成"最容易被当成"通过"，因为
默认值、空列表、异常捕获都倾向于那个方向；而它一旦被当成通过，
整条质检链就变成了装饰。所以：

* `unchecked` 的结论 `passed` 一律为 `False`（`IdentityVerdict.__post_init__` 强制）；
* 判定用**逐角色最低分**而不是平均分 —— 否则"主角漂了但配角很准"会过关；
* 解析不出来 ≠ 通过：调用成功但格式不对，是格式偏差；调用失败，
  是没查成。两者分开处理。

## 多张脸谁当准

真实现场：某个角色的主形象被模型的内容护栏拒了，你换三家模型各出一张，
产物目录里躺着三张脸 —— **谁当准，后面十几集全跟着走**。
`core/faces.py` 是纯函数层的裁决：

排序按 **来源 > 类别 > 新旧**：

```python
SOURCE_RANK = {"user": 0, "pack": 1, "asset": 2}   # 用户钉的 > 参考图包在用的 > 散落产物
KIND_RANK   = {"角色": 0, "": 1, "服装": 2}         # 主形象才是那张脸的准绳
```

自动定的条件（能不打扰人就不打扰）：

* 基准是**用户钉过的**或**参考图包在用的** → 已经表过态，直接采信；
* 基准只是散落产物，但跟它一致的占多数 → 多数派说了算；
* 否则 → `ambiguous`，**停下来问人**，并且只问定不了的那些。

一个容易忽略的边界：`matches_character()` 处理名字包含关系 ——
`朱锦` 与 `朱锦娘` 同在剧里时，娘出场不能让锦也被锁上。

**这一层已经从"猜"改成"问"了**：分镜阶段的模型显式输出
`Shot.characters = [name, ...]`，顺序即"谁在画面里更重要"。名字子串匹配降级为
**退路**：只有旧 `episode.json`（这个字段还不存在的年代）或模型漏了字段时才走它，
而且 stage02 会把"靠猜的镜数"报出来 —— 否则用户会把"能跑"当成"猜得对"。

两个容易写错的细节：

* **`None`（没声明）和 `[]`（声明画面里没人）是两回事。** 合并成一种，要么空镜
  被迫锁一张不该出现的脸，要么所有旧 `episode.json` 都被当成空镜、一个人都不锁。
* **锁脸跟着声明走，告警跟着并集走。** "出镜人数超过参考图上限"这条告警按
  "声明 ∪ 文本推断"算：模型少声明一个人时如果告警也跟着变少，它就变成
  "只要模型不写就永远不报警"——比没有还糟，因为它训练人相信"没告警就是没问题"。

**余下的薄弱点**：`characters` 里仍然按**名字**匹配角色。同名不同人、改名、
多重身份（卧底）还是会错配 —— 要做扎实得给每个角色一个稳定 id，
再用脸/姿态检测在关键帧上回归验证。

## 单段时长是模型的约束，不是创作的约束

`core/media.estimate_shot_seconds()` 从台词长度和景别反推时长 ——
那是**创作舒适区**（"这句台词要念这么久"），不是生成模型的硬上限。

生成模型的上限来自 provider 自己声明的 `caps.max_duration`（或
`config/models.yaml` 里的同名条目）。超了就由 `plan_shot_split()`
**均分拆段**，逐段渲染后拼接：

```
8 秒的镜头 / 上限 3 秒  →  [2.667, 2.667, 2.666]   ← 总和必须等于原时长
```

拆段有三个容易写错的地方，骨架里都有对应处理：

* 一个镜头中途失败，**已经渲好的分段要删掉** —— 半套分段拼出来的时长是错的；
* 逐段的 usage 要合并上报，否则成本漏记；
* 逐段的 seed 用 `hashlib.md5` 而不是内置 `hash()` —— 后者对字符串加随机盐，
  换一个进程结果就变了，断点续跑会渲染出不一样的画面。

## 质检为什么是流水线的必要环节

参考项目 `domain/realism.py` 的复盘值得抄在这里：

> 早上 7 张主形象的脸没听这套（提示词里写了毛孔雀斑，出来还是磨皮脸）。

结论是**光在提示词里写清楚是没用的**，必须三件事一起上：提示词硬约束、
描述清洗、生成后校验不合格重生成。所以质检不是"可选增强"。

`stages/stage08_qc.py` 跑的是**确定性质检**（不调模型）：时长边界、
重复镜头、景别单调、画面提示词里混进听觉信息、素材缺失。
规则全在 `config/qc_rules.yaml`，**数据不是代码**。

两条来自实战的约束：

1. **规则必须有作用域**（`applies_to` / `stages`）。参考项目把"广告法
   极限词"规则应用到剧本台词上，结果"最强/绝对/第一"全部判死，模型
   花了三个会话、四十多元把 60 集重写了一遍。
2. **不认识的配置键要报错**，不能静默忽略 —— "改了配置没生效"是
   最难发现的一类问题。`python run.py rules` 会把生效来源打出来。

## 口型同步：一个"骨架验契约"的例子

`stages/stage06_lipsync.py` 是自己写的，`LipSyncProvider` 是第六种形态。
它值得单独讲，因为它示范了这个骨架对待第三方适配器的态度：
**契约如果只写在文档里，就等于没有。**

两条契约：

1. 输出**不带音轨**（音轨由 concat 统一铺一次，否则每句台词说两遍）；
2. 输出**时长等于输入片段**。

第 2 条会毁掉整条时间轴：`stage07_concat` 的音画对齐是按 ffprobe 量出的
**片段实际时长**累加的，lip-sync 一改时长，后面所有镜头的声音都会错位 ——
而且全程不报错。

所以骨架不是"信任适配器"，而是：**先让 provider 写到临时文件，ffprobe
量完对得上（容差 0.12s）才原子替换成正式产物**。对不上就这一镜算失败、
临时文件删掉，可以单独重跑，但错的进不了成片。
`tests/test_lipsync.py` 里有两个**故意写坏的 provider**（产 4 秒的、
什么都不写的）来证明骨架真的会拒收。

三项相关的设计：

* 只处理**有台词的镜头**（空镜没有可对的嘴，送过去只是白花钱）；
* 没配 provider 是合法的，但阶段报告里必须有 `[!]` ——
  "成片里嘴型没对上"不能只活在某个人的记忆里。要变成硬门槛就打开
  `qc_rules.yaml` 的 `require_lipsync`，它查的是**产物在不在**，
  不是 provider 报没报成功（报告可以是假的，磁盘上的文件假不了）；
* dryrun 的占位实现**不做任何视觉伪造** —— 只做无音轨重编码并自陈
  "没有真的改嘴型"。试过在画面上叠个波形条表示"已同步"，结论是
  一个看起来同步过的假标记比什么都不做更糟。

## 已付费的任务：为什么 job_id 必须落盘

视频生成是整条链最贵的一环，而"提交成功"到"拿到文件"之间隔着几分钟排队。
进程在这个窗口里死掉（Ctrl-C、断电、容器被回收）是完全正常的事，
问题在于**死掉之后会怎样**：

```
提交成功 -> 排队 -> [进程没了] -> resume -> 又提交一次 -> 又付一次钱
```

而厂商那边其实已经有一份在跑了。第一版骨架就是这个行为 —— job_id 只活在
`_render_shot()` 的局部变量里。修法很小：`Store` 的 shots 表多一列 `job_ids`
（JSON，按拆段序号存），提交成功后**第一件事是落库**，然后才去轮询；
`resume` 先认领记录里的任务，认领得到就不重新提交。

### 两个必须区分开的语义

**"厂商说失败"和"我们等不下去"不是一回事。**

* 厂商报失败 = 终局。记录必须清掉，否则这一镜会被永远认领到一个死任务上，
  每次 resume 都失败 —— 坏记录比没有记录更难查。
* 我们轮询超时 = 任务多半还在厂商那边跑。记录**必须留住**，
  丢掉它就等于重复付费。

第一版 `_poll_one()` 把两者都返回 `failed`，调用方无从分辨，只能一律丢掉 ——
也就是一律重复付费。现在它返回三态 `done` / `failed` / `timeout`。

配套的两个细节：

* 恢复轮询的等待上限（`AI_DRAMA_RECOVER_TIMEOUT`，默认 180s）**明显短于**
  正常轮询（900s）。这是恢复而不是渲染：任务要么早跑完了（一问就有），
  要么早就没了（一问就报错）。为一个可能不存在的任务把整条流水线卡 15 分钟，
  比重新提交还贵。
* 超时路径**不清理已完成的分段**。`_cleanup_parts()` 的理由是"半套分段拼不出
  正确时长"，那针对的是"这段已经没救了"；超时不属于这种情况，而那些分段是
  已经付过钱、完整可用的文件，删掉就等于保证下次再付一遍。

### 对 provider 实现方的一层新要求

`poll` 必须能被一个**从没提交过这个任务**的进程调用（只要厂商侧还能按 id 查
状态）。而且"查无此人"要返回 `("failed", {}, "job not found")` 这种终局状态，
**不要抛异常、也不要返回 running** —— 抛异常会被上层的容错轮询吞掉并一直重试，
于是骨架把"任务没了"误判成"还在排队"，这一镜就永远认领不到也渲不出来。
契约写在 `providers/base.py` 的 `VideoProvider.poll` docstring 里。

`tests/test_job_ledger.py` 用 `KeyboardInterrupt` 模拟"进程在等待中被 Ctrl-C"
（`_poll_one` 只吞 `Exception`，所以这一下真能穿出去），然后把
"resume 不再 submit、只去 poll 那个记录的 id"钉死。CLI 的 `status`
会把未结算任务列出来 —— 否则用户只会觉得"怎么又扣了一次钱"。

## 字幕：两个容易做错的地方

**一、时间轴不能算第二遍。** 字幕飘掉几乎永远是"字幕自己又算了一遍时间"。
音画对齐那一步已经按 ffprobe 量出的**实际时长**累加出了每句台词的起点，
字幕必须复用同一个累加结果 —— `stages/stage07_concat.py` 就是在那个循环里
顺手生成字幕的，并把结果落成 `timeline.json`。这份文件的价值在排查：
字幕飘了，第一件事是打开它，看每个镜头的起止秒数跟你以为的是不是一致。

**二、libass 读 SRT 时，字号不是像素。** 它会假定脚本坐标系是 384x288，
于是 `force_style` 里的 `FontSize` / `MarginV` 都按 (视频高度 / 288) 放大。
实测 720x1280 下 `FontSize=22` 渲染出约 90px 的字、`MarginV=40` 直接糊在画面
底部；同一个字号换到 1080p 又是另一个大小。加 `original_size=` 不管用 ——
它声明的是"这份字幕是按多大尺寸排的"，不改变坐标系。

所以本骨架**自己生成 ASS**，把 `PlayResX/PlayResY` 设成视频的真实尺寸
（`media.probe_size()` 从成片量，不拿 provider 声明的尺寸顶替 —— 中间任何一步
改了分辨率，声明值就和实际对不上了）。字号与边距因此是真正的像素，
同一套比例参数在竖屏横屏上都成立。

顺带三条来自实做的取舍：

* **剧本行不是字幕**。`苏蔓：（低声）不对。` 里的说话人和表演提示是给配音看的，
  烙到画面上就是业余 —— `media.speech_text()` 去掉它们；去完什么都不剩时
  退回原文，显示一句带提示的台词总比显示空白强。
* **烧录不等于字幕**。SRT 一律写出来当交付物（多数平台要的是字幕轨而不是
  烙在画面上的字），烧不烧是另一个开关。
* **"字幕文件生成了"不代表画面上有字**。滤镜写错、路径没找到、字体缺字，
  ffmpeg 全都不会报错，它只是什么都不画。所以测试里有一条**像素级**断言：
  台词那一秒的画面下方必须有亮像素，而没有台词的镜头同一位置必须是干净的。

## 画面校验：为什么它的默认值必须和别处相反

`core/qc.py` 是纯函数、离线可测，它只能查"骨架有能力确定的事"—— 时长、
对白长度、重复、钩子。有两件事它永远确定不了：**画面里有没有字**，
**人像不像定妆照**。这两件要有人真的看一眼。

于是多了第七种形态（`VisionProvider`），而它和另外六种在默认值上刻意相反：

| | 没配环境变量时 | 为什么 |
|---|---|---|
| text / image / video / audio / t2i / lipsync | `dryrun` | 零配置也要能端到端出片 |
| vision | **关闭** | 一个"假装看过了"的默认检查器比没有检查器**更糟** |

第二行是这一层的全部要点。`unchecked`（没查成）和 `pass` 的区别正是质检那一层
存在的意义；一个默认就能返回 `{"pass": true}` 的检查器会把前者洗成后者，
而且报告上会印着一个漂亮的分数。所以 `DryRunVisionProvider` 直接抛
`ProviderError` —— 要检查画面，就必须显式配一个真能看的。

四种情况都归到"没查成"，一种都不许变成"通过"：

```
没配 AI_DRAMA_VISION        -> 没查成
调用失败 / 超时             -> 没查成
模型输出读不出来            -> 没查成
模型说"我看不清这张图"      -> 没查成
```

它们有一个共同点：**你并不知道画面到底有没有问题**。写成"通过"，
成片就会带着从没被检查过的镜头交付，而且连痕迹都没有。

三条来自实做的取舍：

* **判定逻辑一行都没有重写。** 提示词用 `core/identity.CHECK_PROMPT`、
  解析用 `parse_identity_verdict`（含逐角色最低分门槛与 `unchecked` 不变式），
  provider 只做"消息进、文本出"。于是最要紧的几个用例
  （输出乱码算不算通过）**不需要任何 API key** 就能测。
* **结论并进同一份 `QcReport`。** 一份报告写"block 0"、另一份文件写
  "画面里有字"，等于没查。三态汇总的优先级那一层已经写好，直接给它 Finding。
* **只报不改。** 判定不触发自动重生成：一次误判就重渲一镜是真金白银，
  而"重渲之后还是不对"的下场是把钱花在同一个问题上。

抽样是**等距**的，不是取前 N 个 —— 取前 N 个会把检查范围永远钉在开头几场，
而后半部恰恰是最容易漂的地方。

## 画幅：一个数字，四处用，零个报错机会

`ProviderCaps` 从第一版就声明了 `aspect_ratios`，`config/models.yaml` 也一直在写
每个模型支持哪些画幅 —— 但**没有任何东西能用上它**：出图和图生视频的 size
是写死在两个调用点里的字面量 `(720, 1280)`。这是那种"数据和代码都在、
中间少一根线"的状态：声明了一个能力，却没有一条路走到它。

把线接上之后，真正的难点不在"支持 16:9"，而在**别让两个地方各算一遍尺寸**：

```
stage03_frames      用 ctx.frame_size 出图
stage04_video       把 caps.size 送进请求体
dryrun 的图生视频    拿请求里的 size 去 image_to_clip()
字幕                从**成片**量尺寸（所以它自动跟着走）
```

前两处只要有一处对不上，出来的片子就会在某一步换尺寸，而**没有任何一步会报错**
—— ffmpeg 会老老实实帮你拼出一个尺寸不一致的片子。所以尺寸只有一个来源：
`run.meta["aspect"]` → `media.frame_size()` → 写进 video provider 的 `caps`。

三条刻意的选择：

* **画幅记在 run 上，不是命令行上。** `--aspect` 在建 run 时落进 meta，
  `resume` 沿用那个值。补渲一个镜头时得到一块不同尺寸的画面，是那种
  "跑完了、片子也生成了、只是内容不对"的失败 —— 没有一步会报错。
* **认不出来就报错，不退回默认值。** 把 `16:10` 猜成 `9:16`，要等到看成片
  才发现。`1280x720` 这种写法也认（写像素和写比例都很自然）。
* **provider 不支持就当场拦。** 声明了 `aspect_ratios` 而里面没有这个画幅，
  在**建 run 之前**抛。悄悄按自己的默认值渲一版，比直接报错糟得多：
  后者只是今天跑不成，前者是钱花了、片子"成功"了、要等人看出来。

验收标准是"三处尺寸一致"（关键帧 / 片段 / 成片），不是"能跑通横屏" ——
漂移正是发生在两处之间，只钉住其中一处没有意义。

## 声音分三类，按"和什么对齐"分

音效是最后补上的一层，而它的分类方式说明了一件事：**声音不该按"好不好听"分，
该按"和什么对齐"分**。

```
台词  每句一条   ┐
音效  每镜 0-3 条 ┘→ 挂在镜头上：共用同一份累加时间轴（stage07）
BGM   全片一条   ──→ 挂在整片上：从头铺到尾，单独走 mux
```

前两种必须跟镜头一一对应，所以它们**共用同一个 offset**。分开算一遍时间轴就是
字幕当初飘掉的同一个错误（见上一节）。响度也因此分层：台词 1.0、音效 0.55、
BGM 0.16 —— 音效和台词一样响就会把台词盖掉，而盖掉台词是观众唯一会立刻发现的
问题。

三条来自实做的取舍：

* **它是第八个 provider 形态，不是 `AudioProvider` 上的第三个方法。** 用量差
  两个数量级：一集 60 个镜头可能有 40 条音效，而 BGM 永远 1 条。塞进同一个
  provider 会让 `doctor` 和成本表都没法读；而供货方通常也不是同一家
  （音效 API 与 TTS / 音乐生成是不同品类）。**可选的形态要能被显式关掉，
  并且关掉时有人说话。**
* **默认关闭，但理由和 `vision` 不同。** `vision` 关是因为一个"假装看过了"的
  默认检查器会把「没查成」洗成「通过」；`sfx` 关是因为用量 —— 默认打开会让每个
  已经跑得好好的项目突然多出几十次调用。两条都写进了
  `registry.DEFAULT_OFF_KINDS` 旁边的注释里，因为**"为什么默认关"和"默认关"
  同样重要**：只写后者，下一个人会觉得这是个 bug 顺手改掉。
* **没配 provider 时报告里必须有一句话。** 分镜里写着"门被撞开"、成片里没有
  那一声，是那种"一切正常"的缺失 —— `stage05` 和 `stage07` 各写一条 `[!]`。

洗数据有两条硬的：模型会把 **BGM 写进 `sfx`**（后果不是报错，而是每一镜都去
合成一段"弦乐" —— 成本翻倍而且听起来像有人在旁边一直按琴键），也会把
**一整句镜头描述**塞进来。两种都在 `stage01` 里挡掉。

验收标准是"**成片里真的听得到**"：量同一秒的响度，对比开关音效两次跑。不是看
`_sfx00.wav` 在不在盘上 —— "文件生成了"和"画面上有字"是同一类错觉，
字幕那次就是这么骗过去的。

## 音色：一次"没人有义务填那张表"的失败

有个漏洞藏了很久，因为**报告里一切正常**：一部剧里所有角色是同一个嗓子。

链路是这样的 —— `Project.voice_map`（角色 → 音色）从设计上就有，
`voice_for()` 也会先查它。问题是**没有任何一步去填它**：角色是
`stage01` 用模型生成的，人从头到尾没机会逐个指定音色。于是每个角色都走到
最后的兜底分支，拿到全局 `--voice`（默认 `female_01`）。42 岁的摆渡人开口
是少女音 —— 这是用户听出来的，不是测试发现的。

修法不是"提醒大家记得填"，而是**在生成角色的那一刻顺手定**：
`core/voice.py` 从 `desc` 与 `anchor_prompt` 里读性别与年龄线索
（`男` / `female` / `42岁` / `四十来岁` / `mid-40s`），选一个音色落进
`voice_map`，理由落进 `voice_notes`。三条边界：

* **人手写的不动。** 自动推断只补空的 —— `project set ... --voice` 定过的
  一律保留，否则人会发现自己定的音色"过几天自己变了"。
* **读不出来就不要猜。** 描述里没有性别线索时留空并报出来，这一集落到
  全局默认音色上。猜错的代价是"观众听出换人了"，留空的代价只是"还没调"。
* **理由要能看见。** `project show <id> -v` 打出 `voice_notes` 里那句
  依据 —— 觉得不对时才知道该改哪条，而不是只看到一个结果。

同一类问题还有一个：**台词没写说话人时，音色无从选起**。`……阿屿？`
没有 `陈默：` 前缀，`speaker_of()` 返回空串，音色只能退回全局默认。
现在分镜定稿后会点名报出来（"这些镜没写说话人，只能用全局音色"）——
提示词的职责是让模型别漏，但**漏了必须有人说话**。

顺带修掉的同族 bug：TTS 原来把整条 `苏蔓：（低声）不对。` 原样送去合成，
于是观众会听见有人念出"苏蔓"和"低声"两个字。字幕要带说话人，**配音不能**。

## 名字是叫法，不是身份

「这一镜里是谁」决定了拿谁的定妆照去锁脸。这个判断经过三代：

```
第一代  在镜头文本里找角色名的子串        —— 朱锦娘 会匹配上 朱锦
第二代  分镜显式输出 shot.characters=[名字] —— 名字仍不是一对一的东西
第三代  shot.characters=[id/名字/别名]     —— 名字只是这个身份当下的叫法
```

第二代留下的三种错配，共同点是**都不报错**：

| 情况 | 名字匹配的表现 |
|---|---|
| 两个角色都叫「林晚」 | 按名字查表只留得下一个，谁的脸被锁上取决于字典的写法 |
| 第 5 集把「苏蔓」改成「苏晚」 | 前面所有引用"苏蔓"的镜头一起失联，第 2 集开始换脸 |
| 卧底真名「陈默」、化名「林晚」 | 故事里两个名字都出现，"这一镜是谁"变成掷骰子 |

`core/cast.py` 把这件事拆成两个概念：**身份**（`Character.char_id`）与
**叫法**（`name` + `aliases`）。解析只做一件事 —— 把一个引用解析成一个角色，
**并说出它是怎么解析的**：

```python
Resolution(ref="林晚", how=cast.HOW_AMBIGUOUS, character=None,
           others=("林晚(char_1)", "林晚(char_2)"))
```

`how` 是 `id` / `name` / `alias` / `ambiguous` / `unknown` 之一。调用方据此
决定这条降级值不值得报警 —— stage02 就把"有多少镜是写名字而不是写 id 认出来的"
印进报告。

### 三个刻意的选择

**id 由名字推导，不抽随机数。** 老 `project.json` 里没有 `char_id`，要在读取时
补上。若补出来的是随机值，同一个文件读两次就得到两套 id，而引用它们的镜头在两个
进程之间会对不上。`sha1(name)` 前缀是幂等的：同一个名字永远得到同一个 id，
`ensure_ids()` 因此可以随便调用。

**认不出来就不猜。** 一个名字对上两个角色时，这一镜**没有参考图**，报告里点名。
这是本文件里唯一一处"宁可少做事"的地方，理由是后果不对称：给错脸观众看不出来
（都是"一个人"），不给脸至少参考图是空的、报告里看得见。

**让模型照抄 id，但允许它写名字。** 提示词里带一张角色表（`char_xxx = 苏蔓：…`），
模型不需要理解 id 是什么，只需要逐字照抄 —— 于是改名不会让引用失联。但它抄错、
或者干脆写名字时，也不该让这一镜静默丢掉参考图，所以名字/别名**一直**是合法引用，
只是会被记成降级。

### 合并：id 定身份

`Project.merge_cast()` 认人时先按 id，再按名字/别名。认出之后如果模型给的名字与
圣经不同，那个名字**记进别名**而不是改掉圣经 —— 这正是"改名"在数据上的样子：

```
圣经    char_sm = 苏蔓
模型写  char_sm = 苏晚, desc="..."
结果    char_sm = 苏蔓（别名：苏晚）   ← 身份没变，图还是同一张
```

没有 id 的新名字按模型写的入册并**发一个 id 回写进圣经**，下一集它就是在册角色。

### 定妆照的路径也按身份记

`Character.ref_image` 存的是**当初那张图的路径**，stage02 复用一张定妆照时先看这
条路径，找不到才退回"拿角色当下的名字去 `project_portrait()` 拼文件名"。名字会变，
文件名不会 —— 靠名字拼路径的话，改名那一刻图还在磁盘上，程序却找不到它，于是
**重画一张脸，而报告仍然写着"沿用项目里的"**。这一条是端到端跑出来的：单元测试
全绿的时候，改名后的第 2 集悄悄换了脸。

已知边界：模型**没给 id 又写错一个字**（苏曼 / 苏蔓）时会被当成一个新角色入册。
这是刻意的 —— 模糊匹配会把「朱锦」和「朱锦娘」合成一个人，那比多一个角色更难
发现。报告里那句"新入册 N 个"就是给人看的信号。

## 资产台账：记忆要落在磁盘上，还得对得上

### 问题：报告里的 `artifacts` 是一份内存里的字典

`StageReport.artifacts` 记着这一阶段产出了哪些文件，但**进程一退就没了**。
下一次问"这张关键帧是哪条提示词、拿哪张定妆照生成的"，答案只剩"没人记得"。

这和前面几件事故是同一个形状：系统看起来一切正常，因为它**不记得自己做过什么**。

### 做法：两条表，一次记账，一次对账

```
assets        一件资产一行：谁生成的（provider / 模型 / 提示词指纹 / sha256）、
              属于哪个阶段、多大、路径
asset_edges   边：ref（作为参考图被用上）/ source（作为素材被合成进去）/
              derive（同一件东西的下一步形态）
```

id 由 `sha1(f"{run_id}\n{相对路径}")[:12]` 推导，**不是随机数**：阶段会重跑，
重跑一次就多一条记录的话台账第二天就没人信了 —— 和 `core/cast.py` 同一条理由。

`ctx.asset(...)` 是唯一的写入点（阶段代码不自己拼 provider 名字，`via="video"`
就够 —— 从 bundle 的槽位里取），`ctx.asset_of(path)` 是查表，不扫盘。

### 为什么 `--check` 是这一层的重点

台账最容易的失效方式不是"写不进去"，而是**漏记一个产出点**：那件东西从此在报告
里是隐形的，而所有检查都通过。`assets <run_id> --check` 就是把台账和磁盘比一遍，
并且**两个方向分开报**：

* 磁盘上有、台账里没有 → 有产物绕过了台账，从此"它哪来的"没答案；
* 台账里有、磁盘上不在 → 记录在说谎，按它找文件会找到空气。

它**只报不改**。自动补记录会把"漏记账的产出点"永远藏起来 —— 那正是要找的东西。

这条检查第一次跑就报出了两个真漏记：`cost_report.json`（流水线收尾时写的，
不属于任何阶段）和场次拼接的 `scene_video.mp4`。

### 两个刻意的减法

* **拆段产物不进台账。** `shot_001_p1_clip.mp4` 这类中间物拼好即删、崩在半路才留，
  它的存在本来就不稳定。记进去只会制造"永远对不上账"的假差异，而真正该被注意的
  差异会被噪点淹掉。花了多少钱在 `costs` 表里，丢不了。
* **项目定妆照不参与对账。** 它住在 `projects/` 里，不在 run 目录里；每次都报一个
  修不掉的差异，等于教人不要看这份报告。

## 查看器：为什么它必须只读，以及它读不出去什么

### 缺的是"看得见"，不是"能跑"

`python run.py web` 是这个仓库唯一的常驻服务。往里加一个"再来一条"的按钮看起来
顺手，代价是把 CLI 里已经解决过一遍的问题全部搬到网页上重做：谁按的、按了几次、
上一次还在跑吗、预算是多少、失败了谁负责。所以**写入口一个都没有**：`do_POST` /
`do_PUT` / `do_DELETE` 一律 405 并回一句"这个服务是只读的"。

页面的职责是把已经落在磁盘上的东西呈现出来：分镜长什么样、关键帧是哪张、字幕落在
第几秒、质检那几条 `unchecked` 到底是什么。

### 它按 URL 读磁盘，所以白名单是**目录级**的

一个能读到 `.env`、API key、数据库、隔壁仓库的进程，不该把这份能力暴露给任何
输入。规则：

```
只有 runs/ 和 projects/ 下的东西可以被读
绝对路径、盘符、任何 ..、点开头的文件、_work/、数据库后缀 → 404
并且 resolve() 之后再比一次（防符号链接指出去）
```

"不存在"和"不许看"回**同一个 404**：分开就等于告诉外面哪些路径是存在的。

### `api.py` 和 `app.py` 分开

前者是纯函数（store + 磁盘 → 可 json 的字典），不起端口就能测；后者只管路由、
Range 和字节。和 provider 层"判定逻辑是纯函数、IO 很薄"是同一条线。

### 两条规矩，和别处是同一条

* **看不见不等于没问题。** 每个文件引用都带 `exists` / `size`：产物被删了，页面
  显示"文件没了"，而不是一张裂图；`unchecked` 也绝不用和 `pass` 一样的颜色。
* **报告说什么就是什么。** 页面不重算任何判定：`qc_state` 来自 `qc_report.json`、
  钱来自 `costs` 表、时间轴来自 `timeline.json`。

### 一条从浏览器那一遍学到的

**API 测试全绿不代表页面上是对的。** 资产那六张卡片第一次截图时全印着
`[object Object]` —— `by_kind` 的值是 `{"count", "bytes"}`，页面却把它当成数字
直接插值。单元测试断言的是"这个数存在"，没有一条会去看它怎么渲染。修完补了一条
把**两边共用的形状**钉住的断言：形状改了会红，页面不再读 `.count` 也会红。
